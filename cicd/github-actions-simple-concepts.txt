HavenBridge GitHub Actions — Simple Concepts and Learning Notes
===============================================================
Purpose
-------

This file is a simple learning reference for the GitHub Actions concepts used
in the HavenBridge CI/CD phase.

It explains what each GitHub Actions concept means, why HavenBridge uses it,
where it runs, and how it relates to the manual commands previously executed
on Syrus.

This is a learning/reference document.

Validation evidence should remain in:

    cicd/evidence/

1. What Is GitHub Actions?
--------------------------
GitHub Actions is GitHub's automation platform.

It allows HavenBridge to automatically perform tasks when events happen in
the GitHub repository.

Example:

    Developer
        ↓
    git push
        ↓
    GitHub
        ↓
    GitHub Actions workflow
        ↓
    automated tests
        ↓
    Docker build
        ↓
    later: image publication and deployment

Instead of manually repeating every validation step after each change,
GitHub Actions can perform those steps automatically.

2. Workflow
-----------
A workflow is the complete automation definition.

For HavenBridge, the first workflow is stored at:

    .github/workflows/ci.yml

Simple meaning:

    Workflow
    =
    "The complete set of automation instructions GitHub should follow."

The workflow currently focuses on Continuous Integration.

3. Workflow File Location
-------------------------
GitHub Actions workflow files live under:

    .github/workflows/

For HavenBridge:

    /home/alabi/projects/havenbridge-ha-service-platform/.github/workflows/ci.yml

The YAML file is NOT executed directly on Syrus.

Do NOT run:

    ./.github/workflows/ci.yml

or:

    bash .github/workflows/ci.yml

Instead:

    edit ci.yml
        ↓
    git add
        ↓
    git commit
        ↓
    git push
        ↓
    GitHub reads ci.yml
        ↓
    GitHub Actions executes the workflow

4. Trigger
----------
A trigger is the event that starts a workflow.

The HavenBridge CI workflow currently runs for:

    push to main

and:

    pull request targeting main

Conceptually:

    Git event
       ↓
    Does it match the workflow trigger?
       ↓
      YES
       ↓
    Start workflow

Because the workflow runs on every push to main, documentation commits can
also appear in the GitHub Actions tab.

For example:

    docs: record GitHub Actions CI foundation validation

appears in Actions because that commit was pushed to main.

The commit message is not the workflow itself. It is the commit that caused
the workflow to run.

5. Job
------
A workflow contains one or more jobs.

The first HavenBridge CI workflow currently has a job called:

    FastAPI Tests

Simple meaning:

    Job
    =
    "A collection of related work performed on one runner."

Conceptually:

    Workflow
       ↓
    Job: FastAPI Tests
       ↓
    individual steps

6. Runner
---------
A runner is the machine that actually executes a GitHub Actions job.

Simple meaning:

    Workflow = instructions
    Runner   = machine following those instructions

For the HavenBridge CI job we currently use:

    GitHub-hosted runner

with:

    runs-on: ubuntu-latest

GitHub creates a temporary Ubuntu environment for the job.

That machine is separate from:

    syrus
    eph-cp01
    eph-cp02
    eph-cp03
    eph-worker01
    eph-worker02

The GitHub-hosted runner exists for the workflow job and is discarded after
the job completes.

7. GitHub-Hosted Runner
-----------------------
A GitHub-hosted runner is a temporary machine provided by GitHub.

For HavenBridge CI it performs work such as:

    checkout source
        ↓
    set up Python
        ↓
    install dependencies
        ↓
    run pytest
        ↓
    build Docker image

Advantages for CI:

    - no runner server to maintain;
    - fresh environment for every run;
    - no direct access to the HavenBridge homelab is required;
    - useful isolation from Kubernetes credentials and infrastructure.

8. Self-Hosted Runner
---------------------
A self-hosted runner is a machine controlled by the HavenBridge environment
rather than GitHub.

It will be introduced later for Continuous Deployment.

The reason is that deployment requires access to the private Kubernetes
environment.

Conceptually:

    GitHub-hosted runner
        =
    build and validation environment

    Self-hosted HavenBridge runner
        =
    private deployment environment

The planned CD runner will eventually perform tasks such as:

    deploy approved image
        ↓
    kubectl apply / update image
        ↓
    kubectl rollout status
        ↓
    HTTPS health validation

9. Why CI and CD Use Separate Runner Types
------------------------------------------
The separation is intentional.

CI does not need Kubernetes administrative access.
CD does.

Simple architecture:

    GitHub-hosted CI
            ↓
    tests / build / validation
            ↓
          GHCR
            ↓
    Self-hosted CD
            ↓
    HavenBridge Kubernetes

This creates a useful security boundary:

    CI runner
    =
    no Kubernetes credentials required
    no homelab network access required

    CD runner
    =
    controlled access to the private Kubernetes environment

GitHub-hosted runners could technically also be used for CD if a secure
private-network connection were created, but the HavenBridge design separates
CI and CD to keep cluster access controlled and easier to understand.

10. Step
--------
A job contains steps.

A step is one individual action or command.

Examples from HavenBridge:

    Checkout repository
    Set up Python 3.12
    Install Python dependencies
    Run HavenBridge API tests
    Build HavenBridge API Docker image

11. uses:
---------
In GitHub Actions YAML, `uses:` means:

    "Use an existing GitHub Action."

Example:

    uses: actions/checkout@v7

Another example:

    uses: actions/setup-python@v6

Simple memory hook:

    uses:
    =
    use an existing reusable action

12. run:
--------
In GitHub Actions YAML, `run:` means:

    "Execute this shell command on the runner."

Examples:

    run: python -m pytest

    run: docker build --tag havenbridge-api:ci .

Simple memory hook:

    run:
    =
    execute a command

13. working-directory:
----------------------
The FastAPI application lives at:

    applications/havenbridge-api

The workflow therefore uses:

    defaults:
      run:
        working-directory: applications/havenbridge-api

Simple meaning:

    "Run shell commands from the FastAPI application directory."

This is similar to manually doing on Syrus:

    cd /home/alabi/projects/havenbridge-ha-service-platform/applications/havenbridge-api

before running:

    python -m pytest

The directory contains:

    requirements.txt
    requirements-dev.txt
    pytest.ini
    tests/
    Dockerfile
    app/

14. Local Virtual Environment vs GitHub Runner
----------------------------------------------
On Syrus:

    cd /home/alabi/projects/havenbridge-ha-service-platform/applications/havenbridge-api
    source .venv/bin/activate
    python -m pytest

The local `.venv` belongs to Syrus.

It is not committed to Git and does not exist on a fresh GitHub runner.

GitHub Actions instead does:

    GitHub-hosted runner
        ↓
    actions/setup-python
        ↓
    Python 3.12 available
        ↓
    pip install requirements-dev.txt
        ↓
    python -m pytest

Therefore the current GitHub Actions workflow does not need:

    source .venv/bin/activate

15. What `python -m pytest` Means
---------------------------------
The command:

    python -m pytest

does NOT run the HavenBridge application itself.

It means:

    Python
       ↓
    run the installed Python module named pytest
       ↓
    pytest discovers tests
       ↓
    pytest executes tests
       ↓
    PASS / FAIL

The `-m` option means:

    "Run a Python module as a program."

Compare:

    Run the application:
        python -m uvicorn app.main:app

    Run the tests:
        python -m pytest

16. requirements.txt
--------------------
Path:

    applications/havenbridge-api/requirements.txt

Simple meaning:

    "Packages the real HavenBridge application needs to run."

Important packages include:

    FastAPI            = API framework
    Uvicorn            = ASGI web server
    SQLAlchemy         = application database layer / ORM
    Psycopg            = PostgreSQL driver
    Pydantic Settings  = configuration loading and validation
    email-validator    = email-format validation

17. requirements-dev.txt
------------------------
Path:

    applications/havenbridge-api/requirements-dev.txt

Simple meaning:

    "Everything developers and CI need for testing."

It first installs:

    requirements.txt

and then adds:

    pytest
    httpx

Conceptually:

    requirements.txt
        =
    application dependencies

    requirements-dev.txt
        =
    application dependencies
    +
    testing dependencies

18. pytest.ini
--------------
Path:

    applications/havenbridge-api/pytest.ini

This tells pytest how to discover HavenBridge tests.

Important rules:

    testpaths = tests

    python_files = test_*.py

    python_functions = test_*

So pytest looks in:

    tests/

for files such as:

    test_health.py
    test_inquiries.py

19. conftest.py
---------------
Path:

    applications/havenbridge-api/tests/conftest.py

This file provides shared pytest fixtures.

It creates a controlled fake database environment so the automated tests do
not need the real PostgreSQL database.

Real application:

    FastAPI
       ↓
    SQLAlchemy
       ↓
    Psycopg
       ↓
    PostgreSQL

Automated tests:

    FastAPI
       ↓
    FakeDatabaseSession
       ↓
    temporary Python memory

This means the first GitHub-hosted CI job does NOT require:

    Kubernetes credentials
    PostgreSQL password
    PostgreSQL SSH tunnel
    homelab network access
    NFS
    Traefik
    MetalLB

20. Pytest Fixture
------------------
A pytest fixture is something pytest prepares for a test.

Example:

    test asks for fake_db_session
        ↓
    pytest finds fixture
        ↓
    fixture creates fake database session
        ↓
    test receives it

21. FakeDatabaseSession
-----------------------
FakeDatabaseSession imitates only the SQLAlchemy Session behavior currently
required by HavenBridge tests.

It supports methods such as:

    add()
    commit()
    refresh()
    rollback()
    scalars()
    execute()

It does not use a real PostgreSQL server.

Instead, test records are temporarily stored in Python memory.

22. FastAPI TestClient
----------------------
TestClient lets tests make requests directly against the FastAPI application
without manually starting Uvicorn.

Instead of:

    python -m uvicorn app.main:app

and then:

    curl http://localhost:8000/health/live

the test can do conceptually:

    client.get("/health/live")

32. Interview Explanation
-------------------------
A concise explanation of the current HavenBridge GitHub Actions design:

    "I use GitHub Actions for HavenBridge CI/CD. The CI workflow runs on a
    GitHub-hosted Ubuntu runner and automatically checks out the repository,
    configures Python 3.12, installs the test dependencies and runs the
    FastAPI pytest suite. The tests use a fake database session, so CI does
    not require access to the private Kubernetes or PostgreSQL environment.

    I separate CI from CD because CI only needs a clean validation
    environment, while deployment requires controlled access to the private
    HavenBridge Kubernetes network. The later CD stage will therefore use a
    self-hosted runner with restricted cluster access."

33. GitHub Actions Permissions for GHCR
---------------------------------------

Before the HavenBridge CI workflow can publish a Docker image to GitHub
Container Registry (GHCR), the workflow must be given permission to write
packages.

The workflow previously used:

    permissions:
      contents: read

This means:

    contents: read
        =
    The workflow can read repository contents.

For GHCR publication, the workflow now uses:

    permissions:
      contents: read
      packages: write

This means:

    contents: read
        =
    Read the HavenBridge repository.

    packages: write
        =
    Publish packages, including container images, to GitHub Packages/GHCR.


GITHUB_TOKEN
------------

GitHub Actions automatically provides a temporary token called:

    GITHUB_TOKEN

The HavenBridge workflow can use this token to authenticate to GitHub
Container Registry.

For this same-repository workflow, a separate Personal Access Token is not
required for the planned GHCR publication.


Security Principle
------------------

Only the permissions required by the workflow should be granted.

Current HavenBridge CI permission scope:

    contents: read
    packages: write

The workflow has not been granted Kubernetes credentials or private homelab
access.


Current GHCR Progress
---------------------

Completed:

    FastAPI tests                         YES
    Docker build validation               YES
    Kubernetes manifest validation        YES
    GHCR package write permission         ADDED

Not yet implemented:

    GHCR login
    GHCR image tag
    GHCR image push


Planned Flow
------------

Validated Docker image
        ↓
GITHUB_TOKEN
        ↓
packages: write
        ↓
Authenticate to ghcr.io
        ↓
Tag image
        ↓
Push image to GHCR


Quick Memory Hook
-----------------

contents: read
    =
read the repository

packages: write
    =
publish packages/container images

GITHUB_TOKEN
    =
temporary GitHub-provided credential used by the workflow

GHCR
    =
GitHub Container Registry


34. GHCR Authentication
-----------------------

Before a GitHub Actions runner can push a container image to GitHub Container
Registry, the runner must authenticate to:

    ghcr.io

HavenBridge uses:

    docker/login-action@v4

The workflow configuration is:

    - name: Log in to GitHub Container Registry
      uses: docker/login-action@v4
      with:
        registry: ghcr.io
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}


registry
--------

    ghcr.io

is the GitHub Container Registry service.


github.actor
------------

    ${{ github.actor }}

represents the GitHub user or automation identity responsible for triggering
the workflow.


GITHUB_TOKEN
------------

    ${{ secrets.GITHUB_TOKEN }}

is a temporary credential automatically created by GitHub Actions for the
workflow.

HavenBridge does not currently require a Personal Access Token for this
same-repository GHCR publication workflow.


Required Permission
-------------------

The workflow includes:

    permissions:
      contents: read
      packages: write

The important permission for publishing container images is:

    packages: write


Current Flow
------------

GitHub-hosted runner
        ↓
GITHUB_TOKEN created
        ↓
packages: write permission
        ↓
docker/login-action
        ↓
authenticate to ghcr.io

Authentication does not publish an image by itself.

Image tagging and image pushing are separate later steps.


35. Restricting GHCR Publication to Main
----------------------------------------

The HavenBridge workflow runs for both:

    push to main

and:

    pull requests targeting main

CI validation should run for both events.

However, container registry authentication and publication should only happen
after trusted code reaches the main branch.

The GHCR login step therefore uses:

    if: github.event_name == 'push' && github.ref == 'refs/heads/main'

Meaning:

    Pull request
        ↓
    Run tests
    Build Docker image
    Validate Kubernetes manifests
    Skip GHCR publication steps

    Push to main
        ↓
    Run tests
    Build Docker image
    Validate Kubernetes manifests
    Authenticate to GHCR
    Later: tag and push image

This creates a boundary between:

    validation

and:

    publication

Future GHCR tag and push steps should use the same condition.


36. Tagging the Docker Image for GHCR
-------------------------------------

After the HavenBridge Docker image passes testing and build validation, the
same image can be given a GitHub Container Registry name.

The CI image currently exists as:

    havenbridge-api:ci

The workflow uses:

    docker tag \
      havenbridge-api:ci \
      ghcr.io/brunobrunt/havenbridge-api:${GITHUB_SHA}


docker tag
----------

The docker tag command does not rebuild the Docker image.

It gives an existing Docker image another name.

Conceptually:

                       ┌── havenbridge-api:ci
                       │
    Same Docker image ─┤
                       │
                       └── ghcr.io/brunobrunt/havenbridge-api:<Git-SHA>


GITHUB_SHA
----------

GitHub Actions automatically provides:

    GITHUB_SHA

This contains the Git commit SHA associated with the workflow run.

Using the Git SHA in the container image tag creates traceability:

    Git source code
        ↓
    Git commit SHA
        ↓
    Docker image
        ↓
    GHCR image tag


Why the SHA Is Useful
---------------------

A SHA-tagged image answers:

    "Exactly which Git commit created this container image?"

Example concept:

    Git commit:
    abc123...

        ↓

    Container image:
    ghcr.io/brunobrunt/havenbridge-api:abc123...


Tagging Is Not Publishing
-------------------------

The docker tag command does NOT upload anything to GHCR.

At this stage:

    Docker image built              YES
    K8s manifests validated         YES
    GHCR authentication configured  YES
    GHCR image tag created          YES

But:

    Image pushed to GHCR            NO

The actual publication requires a later:

    docker push


Main Branch Restriction
-----------------------

The image-tagging step uses:

    if: github.event_name == 'push' && github.ref == 'refs/heads/main'

Therefore pull requests continue to perform validation but do not enter the
registry publication path.


37. Publishing the Docker Image to GHCR
---------------------------------------

After the validated HavenBridge image has been tagged with its GHCR name,
the image can be uploaded to GitHub Container Registry.

The workflow uses:

    docker push \
      ghcr.io/brunobrunt/havenbridge-api:${GITHUB_SHA}


docker push
-----------

The docker push command uploads a locally available Docker image to a
container registry.

For HavenBridge:

    GitHub-hosted runner
        ↓
    havenbridge-api:ci
        ↓
    docker tag
        ↓
    ghcr.io/brunobrunt/havenbridge-api:<Git-SHA>
        ↓
    docker push
        ↓
    GitHub Container Registry


Build, Tag, and Push Are Different
----------------------------------

docker build
    =
create the container image

docker tag
    =
give the existing image another name

docker login
    =
authenticate to the container registry

docker push
    =
upload the image to the registry


Build Once
----------

The HavenBridge CI workflow does not rebuild the application before
publication.

The preferred flow is:

    Build once
        ↓
    Run validation
        ↓
    Tag the validated image
        ↓
    Push the same image

This ensures that the container artifact being published is the same image
that passed the CI pipeline.


SHA Image Tag
-------------

The published image will initially use:

    ghcr.io/brunobrunt/havenbridge-api:${GITHUB_SHA}

This provides exact traceability between:

    Git commit
        ↓
    GitHub Actions workflow
        ↓
    Docker image
        ↓
    GHCR package


Publication Restriction
-----------------------

The push step uses:

    if: github.event_name == 'push' && github.ref == 'refs/heads/main'

Therefore:

    pull request
        =
    validation only

    push to main
        =
    validation plus GHCR publication


Semantic Versions
-----------------

Git SHA publication does not replace Semantic Versioning.

Future intentional releases can give the same image an additional tag such
as:

    ghcr.io/brunobrunt/havenbridge-api:v0.2.0

Therefore the same image may eventually have:

    v0.2.0
        =
    human-readable application release

    <Git-SHA>
        =
    exact source-code revision


38. Detecting HavenBridge API Changes
-------------------------------------

The HavenBridge CI workflow now checks whether files under:

    applications/havenbridge-api/

changed during a push.

This prevents documentation-only or unrelated repository changes from
publishing a new HavenBridge API container image.


Git History
-----------

The checkout step uses:

    with:
      fetch-depth: 0

This gives the runner enough Git history to compare the commit before the push
with the new commit.


Change Detection
----------------

The workflow runs:

    git diff --name-only "${{ github.event.before }}" "${{ github.sha }}"

This asks Git:

    "Which files changed between the previous commit and the current commit?"


github.event.before
-------------------

    github.event.before

represents the Git commit before the push.


github.sha
----------

    github.sha

represents the current Git commit associated with the workflow run.


Filtering for the API
---------------------

The changed-file list is checked using:

    grep -q '^applications/havenbridge-api/'

Meaning:

    Look for any changed path beginning with:

    applications/havenbridge-api/


Possible Results
----------------

If an API file changed:

    changed=true

If no API file changed:

    changed=false


GITHUB_OUTPUT
-------------

The detector writes its result to:

    $GITHUB_OUTPUT

For example:

    echo "changed=true" >> "$GITHUB_OUTPUT"

Because the step has:

    id: api_changes

later workflow steps can read the result as:

    steps.api_changes.outputs.changed


Conditional GHCR Publication
----------------------------

The GHCR login, tag, and push steps use:

    if: github.event_name == 'push' &&
        github.ref == 'refs/heads/main' &&
        steps.api_changes.outputs.changed == 'true'

In plain English:

    Was this a push?
        AND
    Was the push to main?
        AND
    Did the HavenBridge API change?

Only when all three answers are YES does GHCR publication occur.


Expected Behavior
-----------------

Documentation-only change:

    git push
        ↓
    CI runs
        ↓
    API changed=false
        ↓
    GHCR login    SKIPPED
    GHCR tag      SKIPPED
    GHCR push     SKIPPED


HavenBridge API change:

    applications/havenbridge-api/... changed
        ↓
    CI runs
        ↓
    API changed=true
        ↓
    GHCR login    RUN
    GHCR tag      RUN
    GHCR push     RUN


Important Distinction
---------------------

CI validation still runs broadly.

Only container publication is conditional.

Therefore HavenBridge continues to run:

    FastAPI tests
    Docker build validation
    Kubernetes manifest validation

even when the API itself did not change.

This keeps CI validation separate from artifact publication.
