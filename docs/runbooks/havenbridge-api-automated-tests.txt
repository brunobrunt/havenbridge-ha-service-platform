PURPOSE
-------

Automated tests check that important HavenBridge API behaviour still works after
code changes.

This document explains why automated tests were added to the HavenBridge API,
what each testing file does, and how to run the tests.

The main purpose of automated testing is simple:

After changing the HavenBridge API, one command checks that important API
features still behave correctly.

Without automated tests, every API endpoint would need to be tested manually
with Uvicorn, curl, the SSH tunnel, and PostgreSQL after every code change.

With automated tests, Pytest performs the checks automatically.


WHAT WAS TESTED
---------------

The current automated test suite checks six behaviours:

1. GET /health/live returns HTTP 200 and reports healthy.
2. GET /health/ready returns HTTP 200 when the database is available.
3. GET /health/ready returns HTTP 503 when the database is unavailable.
4. POST /api/v1/inquiries accepts a valid inquiry and returns HTTP 201.
5. POST /api/v1/inquiries rejects an invalid email address with HTTP 422.
6. GET /api/v1/inquiries returns previously created test inquiries.


IMPORTANT TESTING DESIGN
------------------------

The automated tests do not use the real Kubernetes PostgreSQL database.

Normal application flow:

FastAPI
    |
    v
SQLAlchemy
    |
    v
SSH tunnel
    |
    v
Kubernetes PostgreSQL

Automated test flow:

Pytest
    |
    v
FastAPI TestClient
    |
    v
FakeDatabaseSession

The fake database exists only while the tests run. It does not change or store
data in the real HavenBridge PostgreSQL database.

Because the tests use a fake database, the following are not required:

- The PostgreSQL SSH tunnel
- Uvicorn
- PyCharm's HavenBridge API run configuration
- A live Kubernetes PostgreSQL connection

STEP 4: SHARED TEST FIXTURES
----------------------------

File:
/home/alabi/projects/havenbridge-ha-service-platform/applications/havenbridge-api/tests/conftest.py

Purpose:

This file prepares reusable tools for the tests.

FakeDatabaseSession
    Acts like a small temporary database during a test.

TestClient
    Sends requests directly to FastAPI without starting Uvicorn.

The production database dependency is replaced with the fake session.

Normal application flow:

FastAPI -> SQLAlchemy -> SSH tunnel -> Kubernetes PostgreSQL

Automated test flow:

Pytest -> TestClient -> FastAPI -> FakeDatabaseSession

The TestClient is not used as a context manager because the context-manager form
would run the FastAPI lifespan. The current lifespan runs
Base.metadata.create_all(), which tries to connect to PostgreSQL.

UNDERSTANDING THE OUTPUT
------------------------

Example:

tests/test_inquiries.py::test_create_inquiry_returns_created_record PASSED

Meaning:

tests/test_inquiries.py
    The file containing the test.

test_create_inquiry_returns_created_record
    The specific test function.

PASSED
    The actual result matched the expected result.


ABOUT THE WARNING
-----------------

The current test output includes a Starlette TestClient deprecation warning.

The warning does not mean the tests failed.

PASSED
    Test succeeded.

WARNING
    A dependency should be updated later.

FAILED or ERROR
    Test did not succeed.

The warning does not block the Dockerization phase.


WHY THIS MATTERS TO HAVENBRIDGE
-------------------------------

The tests provide a repeatable safety check before:

- Building a Docker image
- Deploying to Kubernetes
- Adding CI/CD
- Changing API routes
- Changing request validation
- Changing database code

Later, the CI/CD pipeline can run:

python -m pytest -v

If a test fails, the pipeline can stop before deploying a broken container.
