TEST 2 — CONTROLLED HTTP 404 TRAFFIC
============================================================

Host:
syrus

Initial verification:

curl -i https://havenbridge.lab/this-route-does-not-exist

Expected and observed application response:

HTTP 404

Controlled traffic generation:

for i in {1..30}; do
  curl -s https://havenbridge.lab/this-route-does-not-exist > /dev/null
done


Prometheus verification
-----------------------

Host:
eph-cp01

Command:

curl -sG \
  http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=sum by (status_code) (
    rate(
      havenbridge_http_requests_total{
        namespace="havenbridge",
        route!~"/health/(live|ready)"
      }[5m]
    )
  )' \
  | jq -r '
      .data.result[]
      | [.metric.status_code, .value[1]]
      | @tsv
    '

Observed example:

200     0
404     approximately 0.058 requests/sec


404 counter verification:

curl -sG \
  http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=havenbridge_http_requests_total{
    namespace="havenbridge",
    status_code="404"
  }' \
  | jq '.data.result'

Observed:

Both HavenBridge API replicas contained a 404 counter series.

The metric labels included:

status_code="404"
route="unmatched"


Grafana validation
------------------

Observed dashboard behavior:

HavenBridge HTTP Responses by Status Code
    HTTP 404 appeared as a separate series

HavenBridge Application Logs
    nonexistent-route requests appeared

HavenBridge 5xx Error Percentage
    remained 0%

Firing HavenBridge Alerts
    remained NO ACTIVE ALERTS

HavenBridge Error Logs
    no 5xx server-error incident was reported

Result:

PASS

The dashboard correctly distinguished HTTP 404 client errors from HTTP 5xx
server errors.


Important interpretation
------------------------

Prometheus:

rate(...[5m])

returns a per-second rate calculated from counter changes during the previous
five minutes.

For example:

0.058 requests/sec

is not a cumulative request count.

Grafana normally uses:

$__rate_interval

so Grafana and a direct fixed [5m] Prometheus query may display slightly
different numeric values.


============================================================
TEST 3 — CONTROLLED HTTP 500 INCIDENT
============================================================

The /test/500 endpoint is disabled during normal HavenBridge operation.


Initial validation
------------------

Host:
syrus

Command:

curl -i https://havenbridge.lab/test/500

Expected normal state:

HTTP 404


Enable controlled test endpoint
-------------------------------

Host:
eph-cp01

Command:

kubectl -n havenbridge set env deployment/havenbridge-api \
  ENABLE_OBSERVABILITY_TEST_ENDPOINTS=true

kubectl -n havenbridge rollout status \
  deployment/havenbridge-api \
  --timeout=180s


Verify controlled endpoint
--------------------------

Host:
syrus

Command:

curl -i https://havenbridge.lab/test/500

Expected and observed response:

HTTP 500


Generate mixed application traffic
----------------------------------

Host:
syrus

Commands:

for i in {1..80}; do
  curl -s https://havenbridge.lab/ > /dev/null
done

for i in {1..20}; do
  curl -s https://havenbridge.lab/test/500 > /dev/null
done


Alert validation
----------------

Host:
eph-cp01

Command:

watch -n 10 '
curl -s http://127.0.0.1:9090/api/v1/alerts |
jq -r "
  .data.alerts[]
  | select(.labels.alertname == \"HavenBridgeHigh5xxErrorRate\")
  | [.labels.alertname, .state, .labels.severity]
  | @tsv
"
'

Observed alert lifecycle:

inactive
    ↓
pending
    ↓
firing

Alert:

HavenBridgeHigh5xxErrorRate

Severity:

warning


Grafana validation
------------------

Observed dashboard behavior:

HavenBridge 5xx Error Percentage
    increased above the configured warning threshold

HavenBridge HTTP Responses by Status Code
    HTTP 500 appeared

HavenBridge Application Logs
    /test/500 requests appeared

HavenBridge Error Logs
    HTTP 500 error entries appeared

Firing HavenBridge Alerts
    changed from NO ACTIVE ALERTS to 1

HavenBridge Recent Pod Restarts
    remained 0

The controlled HTTP 500 response demonstrated an application error without
requiring a container crash.


Notification validation
-----------------------

Alertmanager successfully routed the firing alert to:

Slack
    #havenbridge-alerts

Discord
    #havenbridge-alerts

Both notification channels received:

HavenBridgeHigh5xxErrorRate — firing

After recovery, both channels also received:

HavenBridgeHigh5xxErrorRate — resolved


Alert timing
------------

The alert evaluates server-error traffic using a rolling five-minute window:

rate(...[5m])

The alert also requires:

for: 2m

before transitioning to firing.

Alertmanager uses:

groupInterval: 5m

Therefore firing and resolved notifications are not expected to occur
immediately after error traffic begins or ends.
