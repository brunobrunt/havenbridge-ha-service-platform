kube-proxy Remediation
----------------------

Before modifying the ConfigMap, a backup was created:

    kubectl -n kube-system get configmap kube-proxy \
      -o yaml \
      > /tmp/kube-proxy-config-before-observability.yaml

The kube-proxy ConfigMap was edited:

    KUBE_EDITOR=vim kubectl -n kube-system edit configmap kube-proxy

The following configuration was changed:

    metricsBindAddress: ""

to:

    metricsBindAddress: "0.0.0.0:10249"

The new configuration was validated:

    kubectl -n kube-system get configmap kube-proxy \
      -o jsonpath='{.data.config\.conf}' \
      | grep -E 'metricsBindAddress|healthzBindAddress'

Result:

    healthzBindAddress: ""
    metricsBindAddress: "0.0.0.0:10249"

etcd Remediation
----------------

Unlike kube-scheduler and kube-controller-manager, etcd was not configured to
listen on every interface.

Instead, localhost access was preserved while each control-plane node's
specific management IP was added.

eph-cp01:

    --listen-metrics-urls=http://127.0.0.1:2381,http://172.16.10.31:2381

eph-cp02:

    --listen-metrics-urls=http://127.0.0.1:2381,http://172.16.10.32:2381

eph-cp03:

    --listen-metrics-urls=http://127.0.0.1:2381,http://172.16.10.33:2381

The three etcd members were changed one member at a time.

After every member restart, cluster health was validated before proceeding to
the next member.


etcd Static Pod Restart Behavior
--------------------------------

etcd took longer to recreate than kube-scheduler or kube-controller-manager.

Observed sequence:

    Running
      ↓
    Terminating
      ↓
    Pending
      ↓
    Running

This is expected because etcd is a stateful distributed database.

During startup it must:

    open its persistent data
    load its WAL and database state
    rejoin its peer cluster
    synchronize with other members
    pass readiness checks

Administrators should therefore allow additional time for an etcd static Pod
to restart before assuming that a configuration change has failed.

Security Considerations
-----------------------

The metrics remediation intentionally made several operational endpoints
reachable over the internal HavenBridge lab network.

These include:

    kube-proxy             TCP 10249
    kube-scheduler         TCP 10259
    kube-controller-manager TCP 10257
    etcd metrics           TCP 2381
    node-exporter          TCP 9100

These endpoints are intended for internal monitoring.

They must not be exposed directly to untrusted or public networks.

Scheduler and controller-manager metrics remain protected by Kubernetes
authentication and authorization.

kube-proxy, node-exporter, and etcd metrics endpoints should be treated as
internal operational endpoints and protected by network-level controls.
