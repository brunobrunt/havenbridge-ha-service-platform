Initial Prometheus Target Validation
------------------------------------

Prometheus successfully discovered both HavenBridge API replicas:

10.244.176.251:8000
10.244.35.66:8000

However, both targets initially reported:

health: down

Prometheus error:

context deadline exceeded

PromQL:

up{namespace="havenbridge",service="havenbridge-api"}

Initial result:

10.244.176.251:8000 = 0
10.244.35.66:8000   = 0


Root Cause
----------

The HavenBridge API Pods were already protected by Kubernetes NetworkPolicy.

The existing ingress policy:

allow-traefik-to-havenbridge-api

allowed Traefik to reach TCP port 8000 but did not permit Prometheus traffic.

Because the HavenBridge API Pods were ingress-isolated, Prometheus could
discover the targets but could not connect to their /metrics endpoints.


NetworkPolicy Remediation
-------------------------

A dedicated ingress NetworkPolicy was added:

allow-prometheus-to-havenbridge-api

The policy allows traffic only when both conditions match:

Namespace:

kubernetes.io/metadata.name=observability

Prometheus Pod:

app.kubernetes.io/name=prometheus
app.kubernetes.io/instance=havenbridge-monitoring-kub-prometheus

Destination:

HavenBridge API Pods

Port:

TCP 8000

This maintains least privilege and does not open the HavenBridge API metrics
port to the entire Kubernetes cluster.

request rates, HTTP errors, response codes, route activity, and P95 latency
using Prometheus metrics.

8. HavenBridge P95 Latency by Route

10. HavenBridge P95 Latency by Replica
11. HavenBridge 4xx Error Percentage

The dashboard uses the following primary HavenBridge metric families:

havenbridge_http_requests_total
havenbridge_http_request_duration_seconds

Kubernetes liveness and readiness probe traffic is intentionally excluded
from application-level Grafana traffic queries using:

route!~"/health/(live|ready)"
