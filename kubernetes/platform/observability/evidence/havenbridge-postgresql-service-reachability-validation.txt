HavenBridge PostgreSQL Service Reachability Validation
======================================================

Phase:
Observability Phase 9 — PostgreSQL Service Reachability Monitoring

Objective
---------
Validate that HavenBridge can detect a PostgreSQL Service connectivity
failure even when the PostgreSQL Pod itself remains Running and Ready.

The validation specifically monitors whether the application PostgreSQL
Service has at least one Ready EndpointSlice backend.

Failure Injection
-----------------

A controlled Service-selector failure was introduced:

  kubectl -n havenbridge patch service havenbridge-postgres \
    --type=merge \
    -p '{"spec":{"selector":{"incident":"postgres-disconnected"}}}'

This added a selector that did not match the PostgreSQL Pod.

The PostgreSQL Pod itself remained Running/Ready, but the application
Service no longer had a Ready backend.

This reproduced the important failure condition:

  PostgreSQL Pod Ready = 1
  PostgreSQL Service Endpoint = 0

Important Observation
---------------------

Kubernetes Pod readiness and Service reachability are different signals.

A PostgreSQL Pod can remain Running and Ready while the application
Service has no usable backend.

This incident also demonstrated that an application may temporarily
continue using an already-established PostgreSQL connection from its
SQLAlchemy connection pool even after the Kubernetes Service selector
has been broken.

Therefore, application readiness alone is not sufficient to prove that
new connections can still be established through the PostgreSQL Service.

The EndpointSlice signal provides independent evidence that the Service
currently has a Ready backend available for new application traffic.

Result
------

PASS

HavenBridge can now detect, alert on, visualize, and recover from the
specific condition where the PostgreSQL Pod remains healthy but the
application PostgreSQL Service loses all Ready EndpointSlice backends.
