=============================================================

Purpose

This note explains the Kubernetes Services currently visible in the HavenBridge

"What is a Kubernetes Service?"

1. What Is a Kubernetes Service?
--------------------------------

A Kubernetes Service gives one or more Pods a stable network address.

Pods are temporary.

A Pod can restart, be deleted, move to another node, or receive a new Pod IP.

Because Pod IP addresses can change, other applications should not normally
depend directly on individual Pod IP addresses.

A Service solves that problem.


Without a Service
-----------------

Imagine an employee works in an office, but the employee keeps changing rooms.

Today:

Employee -> Room 101

Tomorrow:

Employee -> Room 206

If everyone has to remember the employee's current room number, communication
becomes difficult.

That is similar to connecting directly to Pod IP addresses.


With a Service
--------------

Instead of asking:

"What room is this employee in today?"

you call the company extension:

Extension 5000

The company phone system knows which room the employee currently occupies.

That is what a Kubernetes Service does.

A Service provides a stable name, virtual IP address, and port, then forwards
traffic to the correct matching Pods.


Simple Building Analogy
-----------------------

Pod
= the employee or office where the application is actually running.

Service
= the permanent company extension or reception desk used to reach that
  employee/application.

Deployment or StatefulSet
= the manager responsible for making sure the required employees/applications
  exist.

NetworkPolicy
= the security rules controlling who may enter which office.

MetalLB
= the public street address that lets outside visitors find the building.

Traefik
= the receptionist who receives visitors and sends them to the correct office.


2. Understanding the Service Columns
------------------------------------

NAMESPACE
= the department or floor that owns the Service.

NAME
= the Service's Kubernetes name.

TYPE
= how the Service is exposed.

CLUSTER-IP
= the stable internal virtual IP used inside the cluster.

EXTERNAL-IP
= an address used by clients outside the cluster when applicable.

PORT(S)
= the network ports exposed by the Service.

AGE
= how long the Service has existed.


3. ClusterIP Service
--------------------

A ClusterIP Service gets an internal virtual IP that is reachable inside the
Kubernetes cluster.

Building analogy:

A ClusterIP is an internal company phone extension.

Examples in HavenBridge include:

- calico-api
- calico-typha
- kubernetes
- havenbridge-api
- havenbridge-postgres
- kube-dns
- metallb-webhook-service


4. Headless Service
-------------------

A headless Service shows:

CLUSTER-IP: None

It does not provide one virtual Service IP.

Instead, Kubernetes DNS can return the identity or address of the actual backing
Pod or Pods.

Building analogy:

Normal Service:
"Call the database department's main extension."

Headless Service:
"Give me the direct office identity of this specific database employee."


5. LoadBalancer Service
-----------------------

A LoadBalancer Service is designed to make a Service reachable from outside the
Kubernetes cluster.

In HavenBridge:

traefik

has:

TYPE:
LoadBalancer

CLUSTER-IP:
10.97.19.4

EXTERNAL-IP:
172.16.10.40

Building analogy:

ClusterIP
= internal company extension.

LoadBalancer external IP
= public street address or main external number.

MetalLB provides the external address because HavenBridge is a bare-metal
cluster.


6. Service Ports
----------------

Ports are the network entry points exposed by the Service.

Building analogy:

The Service is the main department number.

Ports are like different extensions or doors for different functions.

20. Most Important Summary
--------------------------

A Kubernetes Service does not normally run the application itself.

Services provide a stable way to FIND and REACH those Pods.

ClusterIP

LoadBalancer
